# Fixtures

Golden test data for the Swift tests. Every fixture file here records what upstream OpenJev
produces at the pinned commit (`dcd2094`, see [THIRD_PARTY.md](../THIRD_PARTY.md)) with the pinned
tokenizer revision. Tests load these files and compare byte for byte where the computation is
exact, or within a tolerance for model outputs. The full strategy is in
[docs/09-conformance-and-testing.md](../docs/09-conformance-and-testing.md).

## What belongs here

Small JSON files written by the scripts in [Tools/fixtures](../Tools/README.md). Fixture files are
never edited by hand: a fixture that needs to change is regenerated. Each file records the
upstream commit and tokenizer revision it came from, so a stale fixture is visible.

| Path | Contents |
|---|---|
| `tokenizer/` | Token ids for a string corpus, with and without special tokens, and decode round trips |
| `chat-prompts/` | `[system, user]` messages and their prompt token ids, with thinking on and off |
| `labels.json` | The 255 single-token choice labels, in order |
| `schemas/` | Requests and the internal schema or the error (with `loc` and message) they produce |
| `system-texts/` | Requests and the system text of each group, chunked and unchunked |
| `templates/` | Groups and their template ids, slot positions and label ids, plus the error cases |
| `groups-and-canvases/` | Requests and their groups, canvas widths and seeded canvases |
| `seeds.json` | Requests, their canonical JSON bytes and their seed integers |
| `distributions/` | Synthetic top-k log-probability maps and the probabilities, confidences and answers they give |
| `policies/` | Requests with `samples`, `steps`, `think` or `sequential` and the reads the engine must make |
| `errors/` | Recorded HTTP responses (status, body, headers) for every error in the wire contract |
| `models.json` | `/v1/models` bodies for each backend |
| `python-json/` | CPython `json.dumps` and float `repr` reference tables for the JSON writer and parser. These come from CPython, not from upstream, and record the Python version instead of the upstream commit. Added by issue #3. |

The model parity data recorded from mlx-vlm (slot log-probabilities for each fixture canvas) is
also generated by `Tools/fixtures` and lives here.

## What never belongs here

- Model weights, tokenizer files or generated caches.
- Images larger than a few kilobytes.
- Expected values written by hand.
